# Design conventions

Reference for the patterns already established in `content-hub-firebase.html`. Follow these when adding new fields, panels, or icons so the app keeps reading as one system rather than accreting one-off styles. This is documentation only — it doesn't run; edit the source file and regenerate `index.html` as usual.

## Colors

All color is driven by CSS custom properties on `:root`, with dark as the default and explicit overrides for `:root[data-theme="dark"]` / `:root[data-theme="light"]` (set by the manual theme toggle, persisted to localStorage). Never hardcode a hex color in a new rule — use the existing tokens:

- `--brand`, `--brand-soft`, `--brand-gradient-h` — MediaShock orange, used for active states, primary buttons, links, focus rings.
- `--surface`, `--surface-alt` — card/modal background vs. sunken field background.
- `--border` — all hairlines and input borders.
- `--text`, `--text-soft`, `--text-faint` — primary copy, field labels, secondary/meta text (in that descending order of emphasis).
- `--danger`, `--danger-soft`, `--good`, `--bad` — status colors (delete actions, goal pacing, etc.)
- `--s-draft-*`, `--s-approved-*`, `--s-scheduled-*`, `--s-posted-*` (`-fg`/`-bg`/`-line` each) — the four `.status-pill` variants. `posted` (blue) is *display-only*: it's never stored on the post, it's computed by `displayStatus(post)` (a past-due `approved`/`scheduled` post reads as "posted" since it should have gone out by now) and only ever appears where a pill is rendered from that helper, not from `post.status` directly. Drafts are deliberately excluded — a past-due draft was never confirmed to actually post, so it stays `draft` rather than silently implying it went out. Always render a post's status pill via `displayStatus(post)`, never `post.status` directly, or a past post will incorrectly keep reading as "Approved"/"Scheduled" forever. The status *picker* inside the Post modal is the one deliberate exception — it edits the real stored value, so it always shows the true `post.status`, never the derived label.

The neutral tokens (`--bg`, `--surface`, `--surface-alt`, `--border`, `--text*`, the draft status-pill, the modal backdrop tint, and the shadow tints) all sit on Tailwind's **Zinc** gray scale, not Slate — Slate has a noticeable cool/blue cast, most visible in dark mode. If you add a new neutral gray, pick from Zinc (`#fafafa/f4f4f5/e4e4e7/d4d4d8/a1a1aa/71717a/52525b/3f3f46/27272a/18181b`, 50→900) rather than eyeballing a new hex. This is deliberately scoped to *neutral chrome only* — the bucket accent-color palette (`DEFAULT_BUCKETS`/`PALETTE_ROTATION`) and the avatar-color palette (`AVATAR_PALETTE`) are categorical hues (indigo/blue/cyan/amber/etc., including one muted slate-600 tone used on purpose as the "Behind the Scenes" bucket's color) and are untouched by this — don't "fix" those into Zinc, they're meant to be distinct saturated colors, not chrome.

## Spacing rhythm

Three tiers, used consistently everywhere a label sits above a field or a group of fields sits above another group:

- **Label → field: `0.35rem`** (`.field-col`, and the gap baked into `#postForm label`/`#ideaForm label`). Never let a label sit as a bare sibling of its field — always wrap it in `.field-col` so it picks up this tight gap instead of a section gap.
- **Within a section: `0.9rem`** (`.form-section`'s own gap) — spacing between fields that belong to the same logical group.
- **Between sections: divider + `1.3rem`** (`.form-section + .form-section`, `.form-section + .modal-actions`) — a hairline `border-top` plus `1.1rem` padding-top, so unrelated groups of fields read as visually distinct blocks instead of one long stack.

## Form sections

The Post and Idea modals are each broken into `.form-section` blocks (currently: Details / Owners / Content for Post; Details / Brief / Stage & Feedback for Idea — the Tasks sections were removed, see below). Sections are separated by whitespace and a hairline divider only (`.form-section + .form-section`) — **no heading text on the section itself.** An earlier version added an uppercase eyebrow label per section, but that was redundant with the fields' own labels and read as clutter; it was removed. When adding a new field, put it in the section it semantically belongs to (or give it its own `.form-section` if none fit), but every field/group still needs its *own* `<label>` — don't rely on the section boundary alone to convey what a block is for. (Fixed one regression from the original section-label removal: Idea's Tasks block had no field label of its own, only the section heading — it now has `<label>Tasks</label>` matching Post's.)

## Icons

All icons in this app -- not just icon-only buttons, any status/type indicator too (activity feed, image-count badges, goal pace, link chips) -- are inline SVG, never emoji or an icon font. This was enforced retroactively in a full sweep; if you ever find a stray emoji being used as an icon, replace it the same way. Convention: `stroke="currentColor"`, `fill="none"`, `stroke-width="1.8"`–`2.4` (bump toward the higher end only for small badge-style icons that need to read at a glance), `viewBox="0 0 24 24"`, rendered at `16x16` for `.icon-btn` buttons or `12x12`–`14x14` for inline status icons. Wrap clickable icon-only buttons in `.icon-btn` (2.1rem square, 1px border, 8px radius, `--surface` background), or a variant like `.emoji-inline-btn` when it needs to sit inside/overlay another field.

**Shared icon constants**: reusable icon markup lives as `var ICON_*` string constants (`ICON_X`, `ICON_X_SMALL`, `ICON_CHECK`, `ICON_CHECK_CIRCLE`, `ICON_ALERT_TRIANGLE`, `ICON_CALENDAR`, `ICON_EDIT`, `ICON_TRASH`, `ICON_LIGHTBULB`, `ICON_ARROW_RIGHT`, `ICON_MESSAGE`, `ICON_LINK`, `ICON_IMAGE`, `ICON_CLOCK`, `ACTIVITY_ICON_DOT`), defined together in one place right before `ACTIVITY_ICONS` (search "shared inline icons"). Reuse one of these for any new icon before drawing a new SVG from scratch. **Ordering gotcha**: these must stay declared *before* anything that builds an object/lookup out of them at module top-level (like `ACTIVITY_ICONS`) -- `var` hoisting only hoists the declaration, not the assignment, so referencing a not-yet-assigned `ICON_*` constant at module-init time silently evaluates to `undefined` (this exact bug shipped once: `ACTIVITY_ICONS` was built above the icon constants, so every activity type silently fell back to the dot icon). Using an `ICON_*` constant *inside* a function body is always safe regardless of where in the file that function is defined, since the function doesn't run until later, after all top-level vars are assigned.

Despite the "retroactive full sweep" above, a literal ⏳ emoji survived in `.ic-stale` (the stale-idea indicator on Kanban cards) until it was caught later and swapped for `ICON_CLOCK` — a reminder that this sweep wasn't actually exhaustive; if you spot another stray emoji anywhere, it's likely just another one that slipped through the same way, not a deliberate exception.

**Standing rule, restated because it keeps getting missed**: this has now happened three times (the original full-sweep, `.ic-stale`'s ⏳, and the broken-image placeholder's 🖼️ below) — a new feature adds a "quick" emoji placeholder, ships, and only gets caught later. Treat it as non-negotiable at write time, not a cleanup pass: **before adding any new status/type/placeholder indicator, check whether an existing `ICON_*` constant already covers it, and if not, draw a new inline SVG in the same convention — never reach for an emoji character as a shortcut, even in CSS `content:` on a `::after`/`::before` pseudo-element.** CSS-only placeholders (no JS-rendered element to attach a real `<svg>` to) still have to follow this: use `mask`/`-webkit-mask: var(--icon-image-mask) ...` (or an equivalent per-icon CSS variable holding the same SVG as a `url("data:image/svg+xml,...")`) with `background-color` for the tint, not `content: "<emoji>"`. Example: `.image-thumb.broken::after`, `.li-preview-media.broken-single::after`, and `#postPreviewCarousel.broken::after` (the broken-image-URL placeholders introduced alongside the preview's `error`-event handling) all originally used `content: "🖼️"` and were converted to this masked-SVG pattern using the shared `--icon-image-mask` root variable, matching `ICON_IMAGE`'s shape exactly so the placeholder reads as the same glyph whether it's JS-rendered or CSS-only. Colored `var(--brand)`, not `var(--text-faint)` — a pasted URL that a plain `<img>` can't render inline is often still a perfectly good *link* (Drive/Photos share page, webpage, etc.), just not one a browser can inline-preview as a raster image; `.image-thumb-link` still wraps it in a working `<a>`. That's a positive/clickable state, not an error, so it shouldn't read as muted-gray "something's broken" the way `--text-faint` does elsewhere.

**Deliberate exceptions** (real emoji, left as-is on purpose -- don't "fix" these): the emoji picker's own category data (`EMOJI_CATEGORIES`) is the feature's content, not UI chrome. The LinkedIn post preview's action row (👍 Like / 💬 Comment / 🔁 Repost / ✈️ Send) is simulating LinkedIn's actual UI as accurately as possible, not our own app's iconography -- converting it to our monotone style would make the preview less accurate, not more consistent.

## Toasts (replaced the blocking alert() dialogs)

`showToast(message, type)` — `type` is `"error" | "success" | "info"` (default `info`). Renders into
`#toastContainer`, a fixed bottom-centre stack at `z-index: 200`, above the auth gate (100) and every
modal, so a toast is never trapped behind one.

This app used to call `alert()` on every write failure — 31 of them. A blocking dialog for
"couldn't save" is the wrong trade: it steals focus, must be dismissed before you can retry, and the
sibling Flowboard had already settled on non-blocking notices. All 31 became toasts.

- **Colour comes from the existing status tokens** (`--good` / `--bad` / `--brand` on the left border
  and the icon), and the icon is a reused `ICON_*` constant (`ICON_CHECK_CIRCLE` / `ICON_ALERT_TRIANGLE`
  / `ICON_MESSAGE`) — no new hexes, no new SVGs, no emoji.
- **`gap: 0` on `.toast` is deliberate**: those shared `ICON_*` constants carry their own inline
  `margin-right`, so a flex gap would double the spacing.
- **The message goes in via `textContent`, never `innerHTML`** — nearly every call interpolates a raw
  Firestore `err.message`.
- **Accessibility is load-bearing here.** `alert()` was announced by screen readers automatically; a
  plain injected `<div>` is not. The container is `aria-live="polite"` and error toasts additionally
  get `role="alert"` so they interrupt rather than queue.
- **Dismissal falls back to a timer, not just `animationend`** — under
  `prefers-reduced-motion: reduce` the animation is disabled and that event never fires, which would
  leave the toast on screen forever.
- Capped at `TOAST_MAX` (3), oldest evicted first, so a burst of failures can't cover the page.

**One `alert()` is left on purpose** — the iOS "Add to Home Screen" instructions in the install
button handler. It's a multi-step instruction the user has to read and then act on *outside* the
page, so a toast that fades after a few seconds would be gone before they finished. Don't convert it.

`flagInvalid(inputEl, message)` sits alongside `showToast` and handles the other half: field-level
validation. It uses the browser's own validation bubble (`setCustomValidity` + `reportValidity`) —
the same UI a blank `required` field already produces — because this app has no inline field-error
styling of its own and inventing one just for this would add a pattern nothing else uses. It exists
because `required` only rejects an *empty* value: a title of `"   "` passes it, the submit handler
then trims it to `""`, and both the Post and Idea forms used to `return` silently, so clicking Save
appeared to do nothing at all. The custom validity is cleared on the next keystroke — without that it
sticks and blocks every later submit.

## Notification dropdown is capped at 30

`renderNotifBell()` sorts client-side then `.slice(0, NOTIF_RENDER_LIMIT)`. The **badge count still
reflects every unread item** — only the dropdown list is capped, so nothing is hidden from the count.

The cap has to happen at render time, not in the query: the query deliberately has no
`orderBy`/`limit` (see "Deliberately queried without `orderBy`" below), and a bare `limit()` without
an `orderBy` returns an *arbitrary* subset rather than the newest ones. Matches Flowboard's
`limit(30)` on its own notifications query. Without this the dropdown grew without bound and got
slower every month.

## Reusable input patterns

- **Chips-with-add-row**: owners use `createOwnerChipInput(inputEl, chipsEl, onChange)` — a small factory returning `{add, set, get}`. Reuse this factory (don't hand-roll a new chip list) for anything that's "add a short label, show it as a removable pill." **Owner chips are snapped to the team roster's spelling on add** (`canonicalOwnerName()`, called at `add()`'s single commit point) — this is not cosmetic tidying: `firestore.rules` decides who may edit a post by comparing the stored owner string against the signed-in person's Google display name, so "sarah lim" instead of "Sarah Lim" locks Sarah out of her own post. A name matching nothing in the roster passes through unchanged, so someone who hasn't signed in yet can still be added. If you reuse this factory for something that is *not* a person, skip the canonicalisation — it's specific to names that have to match an identity.
- **Checklist-with-assignee (currently dead code, not wired up)**: `createTaskListInput(listEl, inputEl, assigneeSelectEl, getOwners)` would drive a checkbox + text + avatar + remove list with an assignee dropdown synced to the item's current owners, but nothing in either modal instantiates it — "Tasks UI is removed for now" per the comments above `currentPostTasks`/`currentIdeaTasks`, which just round-trip whatever's already saved so existing data isn't lost. Don't build an assignment-notification feature against this function without first re-wiring it to real DOM elements.
- **Mention autocomplete**: `wireMentionAutocomplete(inputEl, menuEl)` — attach to a feedback textarea plus its sibling `.mention-menu` element; shows up to 5 `teamRoster()` matches as the user types after `@`, inserting `@Name ` on click. Used by both feedback textareas; see "Notifications" below for how the resulting `@mention` actually gets someone notified.
- **Emoji picker**: `createEmojiPicker(toggleBtn, pickerEl, tabsEl, gridEl, textarea, onInsert)` — instantiate one per textarea that should support inserting an emoji (Post Copy, Idea/Brief). The trigger button lives inside a `.textarea-emoji-wrap` (position: relative wrapper around the textarea), overlaid bottom-right via `.emoji-inline-btn`, so it reads as part of the text field rather than a separate toolbar action.
- **Avatars**: `avatarHtml(name, sizeClass)` — always derive color and initials from `avatarColorFor(name)` / `getInitials(name)`, both hashing the trimmed/lowercased name, so the same person renders identically everywhere in the app. Never assign an avatar color ad hoc. In the post card's compact `.pc-meta` row, multiple owner avatars overlap (`.pc-meta .avatar-icon + .avatar-icon { margin-left: -0.5rem }`, plus a `var(--surface)` border on every avatar-icon there as a cutout ring) to save horizontal space — this is scoped to `.pc-meta` specifically, not applied to `.avatar-icon` globally, since owner chips and the feedback log still want normal spacing next to a name/date label.
- **Image links**: both Post and Idea images are entered as pasted URLs (`.image-link-row` input + Add button, `.image-link-grid` of `.image-thumb` tiles with a `.image-remove` button), not uploaded files — deliberately. Firestore documents have a hard 1MiB limit, and embedding uploaded images as base64 forced heavy compression that was visibly pixelated; a URL is a few bytes regardless of the source image's real quality. A thumb gets `.broken` (via the `<img>`'s `error` event) when its URL doesn't load — note `.image-thumb.broken::after`'s decorative placeholder icon must keep `pointer-events: none`, or it silently eats clicks meant for the remove button underneath it. Thumbs are `draggable="true"` (with `draggable="false"` on the inner `<img>`/`<a>` so the browser doesn't hijack the drag into an image-drag instead) — `dragstart`/`dragover`/`drop` on `.image-thumb` reorder the images array via `.splice()`. Post and Idea now share the exact same classes/behavior (`renderPostImageGrid()` / `renderIdeaImageGrid()` are separate functions with separate state, `currentImages` vs `currentIdeaImages`, but identical markup and CSS) — Idea's version used to be a distinct older `.idea-image-*` implementation with no Drive-link detection and no drag-reorder; it was unified onto Post's classes/behavior after a report that pasting a Drive folder link in Ideas rendered a broken-image icon instead of the folder chip Post already showed. If you touch one of these two functions, check whether the other needs the same fix.
- **Post/Idea images list doubles as the asset-folder handoff**: there's deliberately no separate "Asset Folder" field anymore (one existed briefly on Posts and was merged back in per feedback that two entry points was confusing). A Google Drive link pasted into the *same* Images input is detected by `isDriveFolderLink()` (matches `drive.google.com`) and rendered as a distinct folder chip (`.image-thumb.folder-link`) instead of a photo thumbnail — full-width (`flex: 1 1 100%` inside the otherwise-square-tile `flex-wrap` grid) with a folder icon and the URL as a CSS-ellipsis-truncated label, since a Drive folder link doesn't encode a human-readable folder name anywhere in it (would need the Drive API to resolve one, which this app deliberately doesn't call). `extractDriveFolderUrl()` pulls just the `https://...drive.google.com/...` substring (trimming trailing punctuation) out of whatever was pasted, so if someone pastes a whole sentence/note that happens to contain a Drive link rather than the bare link, both the label and the actual `href` only ever show/use the real URL, not the surrounding text. Clicking the chip opens the link in a new tab. On Posts it's excluded from the LinkedIn preview (`getPreviewImages()` filters it out) and from the photo-count badge, and is still picked up by `findAssetFolderUrl()` to drive the calendar card's quick-open folder icon. `post.assetFolderUrl` (the old dedicated field) is kept only as a fallback inside `findAssetFolderUrl()` for any posts saved while that field existed — there's no editor for it anymore, don't resurrect one; new Drive links go in Images.
- **Status picker, a custom dropdown**: `#f-status` is a *hidden* `<input>` holding the real value -- the visible UI is `.status-picker` (button + popup `role="listbox"`), because no browser lets you style `<option>` elements as pills. The trigger shows the current value as a real `.status-pill` (identical markup to the calendar's status badges); the popup list shows each option the same way. `updateStatusSelectStyle()` syncs the trigger's pill whenever `fStatus.value` changes (on selection, or when set programmatically on modal open/reset) -- call it any time you set `fStatus.value` directly, since a hidden input doesn't fire native `change` events. (History: first tried skinning the real `<select>` into one big pill -- reverted, unwanted. Then tried just tinting the select's background/border -- reverted again once the user asked for the *options* themselves to be pill-shaped like the calendar, which a native select can't do at all. This custom-dropdown version is the one that stuck.) If you build another "picker where each choice should look like its own status pill," follow this pattern rather than fighting `<select>` styling again.
- **Color-coding icons by category**: when a set of icons represents different *kinds* of the same thing (activity feed action types being the example -- created/updated/deleted/moved/feedback), color them by category using existing tokens rather than leaving them all one muted color, or they blur together at a glance. Pattern: a `ACTIVITY_ICON_CLASS` map alongside the icon map, applied as an extra class on the icon wrapper (`.activity-icon.act-created` etc.), not inline styles. Current mapping: green `--good` = created, brand orange `--brand` = updated, red `--bad` = deleted, blue `--b-case` = moved/stage-changed, indigo `--b-news` = feedback/comment -- the `--b-*` tokens are just spare named colors already in the palette (seed colors for default content buckets), reused here for variety since they aren't live-bound to any specific bucket at render time.

## Tasks (removed from the UI, kept in the data)

The assignable Tasks checklist (on both Post and Idea) was removed from the form for now, per direct feedback that it added clutter. The `tasks` field is still read on load and passed straight back through on save (`currentPostTasks` / `currentIdeaTasks` — plain variables, not editable) specifically so existing saved tasks aren't lost even though there's no editor for them. The `createTaskListInput()` factory is still defined but unused; re-adding the UI later is mostly restoring the HTML block removed from both forms and re-wiring those two variables back to the controller.

## Growth goals (multi-goal)

Goals live in a `goals` collection, **one document per metric, keyed by the metric name as the doc ID** (`goals/followers`, `goals/impressions`, etc.) — this is what makes "one active goal per metric" automatic: saving a goal for a metric is just `setDoc(doc(goalsCol, metric), {...})`, which always overwrites that metric's single doc, so duplicates are structurally impossible without extra validation code. Capped at `MAX_GOALS = 3` total, enforced at save time in the submit handler (checked against `currentGoals.length`, only when the save would *add* a new metric rather than edit an existing one) — there's no cap on the read/render side, so if that constant ever changes, existing over-the-old-cap data (there shouldn't be any) would still render fine.

The Metric dropdown in the modal *is* the goal picker: selecting a metric loads whichever goal already exists for it (or blank fields if none), so there's a single form for both creating and editing rather than separate flows. Clicking a rendered `.goal-card` opens the modal pre-selected to that card's metric. The toolbar "Set Goal" button opens it defaulted to a metric that doesn't have a goal yet, so it naturally starts a new one instead of landing on an existing goal at random.

There's a legacy `settings/goal` single-document goal that predates this (from before multi-goal support) — kept only for a one-time migration (see `goalsMigrationChecked`): the first time the `goals` collection snapshot comes back empty, it reads the legacy doc once and, if it has valid data, writes it into the new collection. Don't remove the legacy read path; it's what stops anyone's already-set goal from silently disappearing when this shipped.

`#goalCardsContainer` is a CSS grid whose column count tracks how many goals actually exist -- `renderGoalCards()` sets its className to `goal-cols-1`/`goal-cols-2`/`goal-cols-3` based on `valid.length` (1 goal = full width, 2 = side by side, 3 = three across), collapsing back to a single column under the same 980px breakpoint `.chart-row` uses. Set via JS class rather than a CSS child-count selector -- simpler, and it's already recomputed on every render anyway.

## Mobile / view-only mode

The app has a real viewport meta tag (`width=device-width, initial-scale=1`) and responsive breakpoints at `980px` and `720px` (see the `@media` blocks near the bottom of the `<style>` block). `720px` is also the line where phones stop being able to create or edit Posts/Ideas — per direct feedback ("On mobile, things will not be editable, only for viewing" -> clarified as "block only Post/Idea editing", not a full lockdown): everything else (Analytics, adding a feedback comment on an Idea, browsing the calendar/kanban) stays fully functional on a phone.

- **`isMobileView()`** (`window.matchMedia("(max-width: 720px)").matches`) is the single source of truth for "are we in the phone breakpoint" on the JS side — always reuse it rather than a second hardcoded width, so the JS gate and the CSS breakpoint can never drift apart.
- **Creation entry points are hidden by CSS alone**, not JS: `#newPostBtn`, `#newIdeaBtn`, `.day-add` are `display: none` inside the `720px` media query. No JS gating needed here since there's nothing to lock, just nothing to show.
- **Opening an existing Post/Idea still works on mobile** — tapping a `.post-card` / `.idea-card` calls the same `openModal()` / `openIdeaModal()` as desktop. What changes is `setPostReadOnly(isMobileView())` / `setIdeaReadOnly(isMobileView())`, called once at the end of each open function (checked at open-time only — resizing/rotating *while a modal is already open* won't flip it live, which is an acceptable edge case, not a bug to fix reactively).
- **Read-only implementation**: text-like fields (`f-title`, `f-copy`, `i-title`, `i-notes`, date/time) get `.readOnly = true` rather than `.disabled`, specifically so the text stays full-contrast and selectable/copyable — this is a *view*, not a disabled form. Fields with no read-only concept (`<select>`, the custom status-picker trigger `<button>`) get `.disabled = true` instead, which is the only option available for those control types. The add-rows and remove-buttons for owners/images/emoji (`.owner-input-row`, `.image-link-row`, `.idea-link-row`, `.owner-chip-remove`, `.image-remove`, `#emojiToggleBtn`, `#ideaEmojiToggleBtn`) are hidden entirely via one shared `.modal.view-only` CSS rule rather than disabled one-by-one in JS, since there's nothing meaningful to show in a disabled-but-visible state for an "add new chip" row. Save/Delete/Send-to-Calendar buttons are hidden (`.hidden = true`), and Cancel's label flips to "Close" so the one remaining action reads correctly.
- **A `.view-only-badge` ("View only" pill)** sits next to the modal title (`#postViewOnlyBadge` / `#ideaViewOnlyBadge`, inside a `.modal-head-title` wrapper alongside the `<h3>`) so the locked state is visually obvious, not just implied by fields being unresponsive.
- **Idea feedback is the deliberate exception**: `i-feedback-input` and `#addFeedbackBtn` are never touched by `setIdeaReadOnly()` and stay fully live on mobile. Adding feedback calls `updateDoc()` directly (it's not routed through the Idea form's own submit handler at all, mobile or not), which is exactly why it can safely stay enabled while the rest of the idea is locked — there's no "save the whole form" step it depends on. *Removing* an existing feedback entry (`.fb-remove`, one per `.feedback-item`, added later) is treated differently: it's hidden by the shared `.modal.view-only` CSS rule alongside the owner/image remove buttons, since deleting someone's comment is destructive in a way that adding a new one isn't — only *adding* feedback survives the mobile lockdown.
- **A new editing control needs BOTH the `.modal.view-only` CSS rule and a JS guard in `setPostReadOnly()`, and `readOnly` on a textarea is not a lock.** `readOnly` stops a *person typing*; it does nothing to stop a script setting `.value` — which is exactly what any "insert this for me" control does. A control added without the CSS rule renders on a read-only mobile post and can rewrite it. Hiding only the trigger isn't enough either: a panel already opened at desktop width stays open when the same modal is reopened on mobile, and its buttons still act. So hide the trigger *and* its panel in the shared `.modal.view-only` selector list (the CSS holds even if the JS guard is bypassed — verified by forcing `hidden = false` from the console), and separately disable the trigger and close the panel in `setPostReadOnly()`. Belt and braces on purpose. Learned from a feature that shipped with neither and was fully able to rewrite a view-only post on a phone.
- **Per-post UI state must be reset in `openModal()`, because the modal is reused rather than rebuilt.** Anything the modal shows *about the post being edited* survives into the next post opened unless something clears it — which means one post's working state appearing under another post's title. `openModal()` already resets `postPreviewPanel`; treat that line as the marker for "this is where per-post UI state gets cleared" and add to it rather than assuming a fresh open starts clean.
- **Autofocus is skipped in read-only mode**: `openModal`/`openIdeaModal` normally autofocus the title field on open; on mobile this was actively harmful, since focusing a field scrolls the (often taller-than-viewport) modal so the field is in view, which shoved the "View only" badge and close button off the top of the screen before the user ever saw them. Both autofocus calls are now wrapped in `if (!isMobileView())`.
- **Narrow-phone layout polish**: any flex row of several buttons (topbar actions, the Analytics header's Set Goal/Export/Import row) needs `flex-wrap: wrap` or it silently forces the whole page wider than the viewport — a flex parent wrapping its own children doesn't help if a *child* row further down refuses to wrap its own contents. `.day-cell`/`.week-col` got `overflow: hidden` at the `720px` breakpoint for the same reason: the month/week grid's columns are sized with an explicit `minmax(2.4rem, 1fr)`, so a post-card's meta row (avatars, badges, status pill) that doesn't fit will overflow its cell rather than stretch the grid — `overflow: hidden` clips that instead of letting it blow out the page's scroll width. When adding new UI, verify with `document.documentElement.scrollWidth <= document.documentElement.clientWidth` at a real phone width (390px), not just eyeballing a screenshot — content can silently exceed the viewport without an obvious visual cue if it's the last element in a row.
- **`.upcoming-item` (the "Upcoming posts" card below the calendar) reflows to two lines on phones**: dot + date/time + status-pill on top (via `order` on the flex children, `.status-pill` pushed right with `margin-left: auto`), then the title forced onto its own full-width line below (`.upcoming-title-text { order: 3; flex: 1 0 100%; white-space: normal }`, overriding the base rule's `nowrap`/`ellipsis`). Stacking the Scheduled/Drafts columns to one on mobile (already in place) wasn't enough on its own — cramming dot+fixed-width date+title+pill onto one line left only ~15-20 characters of real width for the title even at full card width, silently chopping most real post titles down to a fragment. Same lesson as the agenda posts: on a full-width phone screen, let the title wrap instead of truncating it.
- **"Top performing posts" collapses from a 5-column table into stacked cards on phones** — the table forced sideways scrolling on a phone (the title cell alone had `max-width: 26rem`, wider than most phone screens). `#topPostsTable` and its `thead`/`tbody`/`tr`/`th`/`td` all switch to `display: block` under `720px` (`thead` hidden entirely), turning each `<tr>` into a bordered card: title full-width and wrapping, date underneath, then Impressions/Eng. rate/Reposts as a small inline stat row. The numeric `<td>`s carry `.tp-stat-label`/`.tp-stat-value` spans (added by `renderTopPosts()`) purely for this — they're `display: none` on desktop where the real `<th>` already labels the column, and only appear once the table stops being a table. Same "let it wrap instead of truncating/scrolling" principle as the agenda posts and the Upcoming posts list.
- **The month/week grid is replaced by an agenda list on phones**, not just shrunk further — a 7-column grid has no room for a real title/avatars no matter how tight the CSS gets. `render()` calls `renderAgenda()` instead of `renderMonth()`/`renderWeek()` when `isMobileView()` is true (same "checked when render() runs, not reactively on resize" rule as everything else here — a real phone user's first render already happens at phone width, so this only matters if you're testing by resizing an already-open desktop session). `agendaDays()` reuses the exact same date-range math as the grid (whole month vs. `startOfWeekMonday()`'s 7 days) so the Month/Week toggle still works, just changes how many days the list spans rather than a grid shape. Empty days are skipped entirely (an agenda that lists every empty day defeats the point); if the whole range has zero posts, one `.agenda-empty` message shows instead. Each day section reuses `postsOn()` + the same `renderPostCard()` as the grid — no separate post-card markup to maintain — with `.agenda-posts .post-card` given more breathing room (larger font/padding, `white-space: normal` on the title so it wraps instead of the grid's ellipsis-truncate) since a full-width phone screen has the room the grid never did. `#weekdayRow` (the grid's column header strip) is hidden at the same breakpoint since it has no grid to sit above once agenda is active.

## Installable app (PWA)

The Content Hub can be installed as a standalone app (desktop and Android via a real Install button; iOS via manual "Add to Home Screen", since Apple has no install API at all) rather than only living as a browser tab.

- **`manifest.json` and its icons/`sw.js` are separate files**, not part of `content-hub-firebase.html` — unlike the rest of the app, these aren't synced from the canonical source. `manifest.json` is hand-maintained, and `icon-192.png`/`icon-512.png`/`apple-touch-icon.png` are generated from `favicon.png` with a **flattened white background** (same fix as the desktop shortcut's `favicon.ico` — see below).
- **The `<head>` links (`manifest`, `apple-touch-icon`, `theme-color`) live in `sync_from_scratchpad.py`'s `HEAD_OPEN` template**, not in `content-hub-firebase.html` itself — that source file has no `<head>` tag at all (it starts at `<title>`, which the sync script uses as an insertion anchor). Any future `<head>`-level addition (another meta tag, a preload hint, etc.) goes in the Python script, not the HTML source, or it will silently never make it into `index.html`.
- **`sw.js` deliberately does no caching** — no `fetch` handler, just `install`/`activate`. This app's content changes constantly (posts/ideas/analytics), so a cache would mean serving stale data; the service worker exists purely because some browsers still check for one as an installability signal, not for offline support.
- **The Install button (`#installAppBtn`, next to the theme toggle) branches on platform**: on Chrome/Edge it listens for `beforeinstallprompt`, stays hidden until that event fires (there's nothing to click before then), and calls `deferredPrompt.prompt()` on click. On iOS (detected via UA sniffing, since there's no feature-detection alternative — `beforeinstallprompt` simply never exists there) it shows immediately on load and just alerts instructions for the manual Share → "Add to Home Screen" flow, since no programmatic install is possible. `isStandaloneDisplay()` (`display-mode: standalone` media query, or `navigator.standalone` on iOS) keeps the button from showing at all once already installed.
- **Testing note**: `beforeinstallprompt` rarely fires in headless/automated Chromium (engagement heuristics), so verifying the button's own logic means dispatching a synthetic `beforeinstallprompt` event with a stub `prompt()`/`userChoice` rather than waiting for the real one — that's testing *this app's* handler, not Chrome's install eligibility itself.
- **The install button can look broken in the desktop shortcut/installed app window** — that's by design, not a bug: `isStandaloneDisplay()` reports true there (`display-mode: standalone`), so the button correctly never appears, since the app is already "installed" from that window's perspective. It only shows in a normal browser tab.

## Live update (auto-reload on new deploy)

Firestore data already updates live everywhere via `onSnapshot` (posts/ideas/analytics/activity/etc.) — the one thing that *doesn't* update on its own is this page's own code, since GitHub Pages has no push mechanism to tell an already-open tab a new version exists.

- **`sync_from_scratchpad.py` stamps a UTC timestamp build version into both `index.html` (as the `CURRENT_BUILD_VERSION` JS constant, replacing the `__BUILD_VERSION__` placeholder that lives in `content-hub-firebase.html`) and a sibling `version.txt`** on every regen. The running page polls `version.txt` (every 60s, plus immediately on tab-focus via `visibilitychange`) and compares it to its own `CURRENT_BUILD_VERSION`; a mismatch means a newer deploy has landed.
- **The real worst-case latency is ~10 minutes, not ~60 seconds.** GitHub Pages serves everything (including `version.txt`) through its Fastly CDN with `Cache-Control: max-age=600`, and confirmed by testing, Fastly ignores the query string when deciding what to serve from cache — so appending `?_=Date.now()` to the fetch does *not* bypass it the way cache-busting normally would, and `{ cache: "no-store" }` only controls the browser's own local cache, not the CDN sitting in front of it. GitHub Pages doesn't support custom response headers (no `_headers` file, unlike Netlify/Vercel), so there's no way to shorten this from the app's side. A tab open when a deploy lands may not see `version.txt` change until the CDN's cached copy naturally expires.
- **A tab that predates this feature can't self-update onto it.** The polling loop only exists in code that's already running — a page loaded before this shipped has no such loop, no matter how long it's left open. It needs one manual reload to get onto a build that actually contains the feature; every deploy after that point is caught automatically.
- **It never reloads out from under an open modal.** `anyModalOpen()` just checks `.modal-backdrop.open` generically (every modal in the app shares that class/toggle, so this doesn't need updating when a new modal is added) — if one's open when a new version is detected, the reload is deferred (`pendingBuildVersion` remembers it) and a second, cheap 5-second interval (`reloadIfPendingAndSafe`, no network call) retries until no modal is open, e.g. right after the user closes it. Losing someone's half-typed post/idea draft to a surprise reload would be a much worse bug than the page code lagging a few extra seconds behind.
- **The placeholder-guard is a regex on the timestamp's shape (`/^\d{4}-\d{2}-\d{2}T.../`), not a literal string match against `__BUILD_VERSION__`.** This bit us once already: Python's `str.replace()` substitutes *every* occurrence of the placeholder text in the file, including inside what was meant to be a literal-string safety check guarding against the placeholder ever leaking through unsubstituted -- silently turning that guard into a no-op that disabled the whole feature. If you ever touch this block, remember any literal occurrence of the placeholder text gets replaced too, not just the intended one.

## Follower vs. visitor demographics

The Analytics tab has two separate demographic panels, not one — "Follower demographics" (who's already following the page long-term) and "Visitor demographics" (who's actually viewing the page/content, a larger and more transient audience). LinkedIn treats these as genuinely different exports, and conflating them into one panel would misrepresent whichever one got overwritten.

- **One shared renderer, two call sites, deliberately different empty-state behavior.** `renderDemographics(demographics, gridId, cardId, emptyMessage)` takes its target element IDs as parameters rather than hardcoding `demographicsGrid`/`demographicsCard`. Follower demographics is called *without* `emptyMessage` and still hides its card entirely when empty (matches its original behavior — it's essentially always populated, by sample data or a basic Followers-only import). Visitor demographics passes an `emptyMessage` explaining it needs LinkedIn's separate Visitors export, so the card stays visible with that message instead of vanishing — hiding it silently would make a real, easy-to-forget prerequisite (a second XLS download) look like the feature doesn't exist at all rather than "not set up yet."
- **`visitorDemographics` mirrors `followerDemographics` everywhere the latter appears** — `SAMPLE_VISITOR_DEMOGRAPHICS`, `buildDefaultAnalyticsData()`, `saveAnalytics()`, the Export Analytics JSON bundle, and Import. If you ever add a third demographic-adjacent field, it needs to be added in all of these places (`content-hub-firebase.html`), not just the render call — nothing enforces this structurally, it's just a parallel convention to keep matching by hand.
- **`agent/import_linkedin_xls.py`** (a separate script, in the *Marketing Manager* repo, not this one) is what actually produces real (non-sample) demographic data from LinkedIn's manually-exported XLS files. It already knows how to tell Followers-kind sheets from Visitors-kind sheets (by which count column is present — "Total followers" vs "Total views"/"view"), and routes each into its own `follower_demographics`/`visitor_demographics` dict, output as separate `followerDemographics`/`visitorDemographics` bundle keys.
- **`splitLegacyDemographics(bundle)` migrates the old merged-with-suffix shape.** Before the Python script was split, both kinds shared one `followerDemographics` object, disambiguated only by suffixing the key with `"(Followers)"`/`"(Visitors)"` (e.g. `"Location (Visitors)"`). This helper detects that shape (no `visitorDemographics` key present, but suffixed keys inside `followerDemographics`) and splits/strips them into the correct two panels. If `visitorDemographics` already has real content, it's a new-format export and nothing gets touched.
- **It runs on every load, not just on Import.** The first version of this only ran inside the Import button's click handler — which meant anyone with real analytics data already sitting in Firestore from *before* this feature shipped would never see it fixed, no matter how many times they reloaded the page, since nothing re-processes already-stored data just because the code changed. It's also called from the `analytics` `onSnapshot` handler (right after `analyticsDataCache = snap.data()`), so existing Firestore data self-heals the moment it's read, the same as freshly imported data — this is a "normalize on read" fix, not a stored-data migration; the Firestore document itself keeps its old shape until something else happens to resave it, and every client just re-derives the same split in memory on each load (cheap and idempotent, so that's fine).

## Empty date-range state

`renderAnalytics()` filters `days` down to whatever the active date-range preset/custom window covers, then feeds that into the KPI row, trend chart, engagement breakdown, takeaways, suggestions, and the data table. If that filtered set is empty — most commonly a stale "Custom" range left over from an earlier session (view state persists per-browser in `localStorage`, so it doesn't reset itself), but any preset can do it if the imported data's dates don't reach that far back/recently — every one of those sections must be explicitly reset to a "No data in this date range" state (`.chart-empty`), not just skipped.

The bug this replaced: the code used to just `return` early when `filtered.length` was `0`, leaving the KPI row/trend chart/etc. showing whatever they'd last rendered. A real, successful Import in that state looked exactly like "the import didn't work" — the numbers on screen genuinely didn't change, because nothing re-rendered them at all, while `#analyticsRange` (computed *before* that early return) correctly said "No data yet." Anyone hitting this would have no way to tell the difference between "import failed" and "import worked, but your date filter is hiding it" without being told explicitly. If you add a new range-dependent section to this tab, it needs its own reset in this same block, or it'll silently reintroduce this bug for that one section.

## Analytics tab layout order

"View as table" (the `#analyticsTable` toggle) sits directly after the Trend/Engagement chart row, *before* Top performing posts and either demographics panel — it's the tabular equivalent of the same chart data, not a general-purpose data dump, so it belongs next to the chart it mirrors rather than stranded after unrelated sections. If you add a new chart-adjacent view like this, place it next to what it's a view *of*, not at the end of the tab by default.

## Suggested next steps (data-driven, not generic advice)

`generateSuggestions()` used to always end with one hardcoded, always-shown bullet ("check the Top Performing Posts table and Key Takeaways together...") regardless of what the data actually said — on accounts where the other rule-based checks didn't fire (engagement/CTR/follower-growth thresholds not met), that boilerplate bullet was often the *only* thing shown, which is exactly as unhelpful as it sounds.

- **Every bullet should name something specific from the actual data** — a real percentage, a real post title, a real day of the week — not generic advice that would apply to any account. The generic "check the table" bullet is now a last-resort fallback, only shown if there's truly no post with `engagementRate > 0` to point to.
- **Content-type comparison uses average engagement rate across all posts, not raw counts in the top 10.** Counting which format appears most in the leaderboard just measures how often you post that format, not whether it actually performs better — comparing per-type averages (with a `>= 3` posts-per-type minimum, and requiring the best average to beat the worst by 20%+) answers the real question.
- **Day-of-week and "best single post" picks both guard against thin/misleading samples.** Day-of-week needs `>= 2` posts for a given day before its average counts, and the same 20%+ gap threshold applies. The single best-performing post is chosen among posts with `impressions >= 50% of the median` — without that floor, a post with one lucky like and almost no reach can out-rank everything else on raw engagement rate percentage and get crowned "your best post," which is misleading rather than useful.
- **Post titles get `.replace(/\s+/g, " ").trim()` before truncating**, not just a length cap — LinkedIn's per-post export titles can contain literal newlines (multi-paragraph posts), and without flattening whitespace first, a title-in-a-sentence reads as several disconnected quoted fragments jammed together instead of one clean snippet. Also goes through `escapeHtml()`, same as the Top Performing Posts table — any post title is untrusted content the moment it's placed in `innerHTML`.

## Sortable data table

`#analyticsTable`'s headers (`.sortable-th`, each with a `data-sort-key` matching a field on the aggregated period objects — `date`, `followers`, `impressions`, etc.) are click-to-sort, toggling ascending/descending on repeat clicks of the same header and resetting to ascending on a new one. `analyticsTableSort` is a module-level var (not local to `renderAnalyticsTable`) specifically so the chosen sort persists across re-renders — a new import, a range/granularity change, anything that calls `renderAnalyticsTable(currentPeriods)` again — rather than silently resetting to date-ascending every time the underlying data changes. The click listeners are attached once at load, not re-bound on every render, since only `#analyticsTableBody` (not the `<thead>`) ever gets replaced via `innerHTML`.

## Post feedback log (mirrors Idea feedback)

Posts now have the same `feedback` array (`{text, date, author}`, add via `.fb-remove`-backed removal) that Ideas have had all along — `renderFeedbackLog(feedback, logEl)` takes the target element as a parameter (same pattern as `renderDemographics`'s gridId/cardId) so one function drives both `#feedbackLog` (Idea) and `#postFeedbackLog` (Post), each with their own add/remove handlers wired to `ideasCol`/`postsCol` respectively.

**The load-bearing fix this required**: the Post form's save was a full-replace `setDoc(doc(postsCol, postId), data)` with no merge flag — unlike the Idea form, which already used `{merge:true}`. Without merge, saving a post through the normal "Save Post" button would silently wipe out `feedback` (and `approvedBy`/`approvedAt`, see below) on every single edit, since neither field is listed in that literal save payload — they're only ever written via their own dedicated `updateDoc()` actions. This was a real, verified bug during QA before the fix (feedback disappeared after a routine title edit) — if you ever add another field to posts that's written via `updateDoc()` outside the main form, confirm it survives a normal Save, or it'll quietter reintroduce this same class of bug.

## Approval trail (approvedBy/approvedAt)

Stamped automatically in the Post form's submit handler, not user-editable directly — comparing the post's *previous* stored status (looked up from the local `posts` cache before saving) against the new status being saved:

- Draft → Approved/Scheduled: stamps `approvedBy` (display name, falling back to email) and `approvedAt` (now).
- Approved/Scheduled → Draft: clears both back to `null` — an old approval doesn't carry over once someone un-approves it.
- Any other transition (Approved ↔ Scheduled, or re-saving with no status change): touches neither field at all, relying on `{merge:true}` to leave whatever's already in Firestore untouched — a routine content edit or moving between the two "already approved" states isn't a new approval event and shouldn't overwrite who actually approved it originally.

Shown as `#postApprovedNote` (styled with the approved-green token, `.approved-note`) next to the existing "Last edited by" note — same visual language, different color so the two don't blur together.

## Global search (topbar)

`#globalSearchInput` sits in the topbar itself, not inside any tab panel, so it's reachable regardless of which tab is active — unlike the Calendar tab's own search (which only ever filtered posts already scoped to that tab), this searches posts *and* ideas together and can jump you to either. Clicking a result reuses the existing tab-switch idiom (`document.querySelector('.tab-btn[data-tab="..."]').click()`, the same trick used elsewhere in this file) before calling `openModal()`/`openIdeaModal()`, rather than a new tab-switching function — the click naturally re-runs the exact same active/hidden toggling logic the real tab buttons use, so there's no second code path to keep in sync.

## One-time onboarding banner

`#onboardingBanner` sits right after `</header>`, inside `#appRoot` (so it never shows before sign-in) but outside every `.tab-panel` (so it's visible no matter which tab loads first, and doesn't disappear on a tab switch). Dismissal is a single `localStorage` flag (`mediashock-content-hub-onboarding-dismissed`) checked once at load — there's no per-account/server-side tracking of who's seen it, so it's "once per browser," not "once per person" (a new browser or a cleared localStorage will show it again).

Posts/ideas collections used to auto-seed a handful of fictional example posts/ideas (`SEED_POSTS`/`SEED_IDEAS`) the first time `postsCol`/`ideasCol` came back empty, as an onboarding aid. That was removed once real content started being entered — the seeded docs were indistinguishable from real ones once created, which made the Calendar/Planner confusing to read at a glance. Don't re-add automatic mock-content seeding; if a similar onboarding aid is wanted again, prefer something that's visibly marked as an example (the way the analytics tab's `.sample-badge` labels its placeholder chart data) rather than real-looking documents mixed into `posts`/`ideas`.

## Schema changes

Any new field on `posts`/`ideas` must be additive and read with a fallback (`post.newField || defaultValue`) — existing documents without it should degrade gracefully, never break. See `normalizedGoal()` for the pattern used when a field's *shape* changes, not just its presence.

Removing a single entry from an idea's `feedback` array (the per-comment `.fb-remove` button) rewrites the whole array via `updateDoc(doc(ideasCol, id), { feedback: list })` on a locally-spliced copy, rather than Firestore's `arrayRemove()`. `arrayRemove()` deletes by exact value match, which is fragile here (relies on `text`/`date`/`author` all matching byte-for-byte) — an index-based splice-and-rewrite is simpler and unambiguous when the array holds plain objects instead of primitives.

An imported post's `id` (from the Import JSON flow, `normalizeImported()`) is stripped down to `[A-Za-z0-9_.-]` before use, falling back to a generated `import-<timestamp>-<idx>` id if that leaves nothing. It's used both as the Firestore doc id *and* interpolated unescaped into `data-id="..."` attributes (Upcoming list, Global search results, idea cards) — an untrusted id from a hand-edited or third-party-exported JSON file could otherwise break out of the attribute. If you add another place that renders a post/idea id straight into an HTML string (rather than via `dataset.id = ...` in JS, which is injection-safe), sanitize at the source in `normalizeImported()` rather than escaping at every call site.

`escapeHtml()` escapes `"`/`'` in addition to `& < >`, so it's safe to use for text dropped into an HTML *attribute* (e.g. `data-url="' + escapeHtml(url) + '"`), not just a text node — keep using it (not a plain string) anywhere user-entered text lands in a built HTML string.

## Activity-log diffs on edit (describePostChanges / describeIdeaChanges)

Editing an existing post/idea logs a field-level diff (`status Draft → Approved, copy edited`, capped at 3 changes via `summarizeChanges()`) instead of a generic "Updated post/idea". `describePostChanges(oldPost, data)`/`describeIdeaChanges(oldIdea, data)` compare specific fields by name — title, status/stage, bucket, date/time, owners, copy/notes, image count. **This list isn't derived from the save payload automatically**: adding a new editable field to the post/idea form won't show up in the activity diff unless you also add a comparison line to the relevant `describe*Changes()` function. A save with no detected field changes (e.g. re-saving without editing anything) falls back to the old generic "Updated post/idea "Title"" message rather than an empty diff clause.

## Feedback/activity timestamps: local date, not sliced ISO

`renderFeedbackLog()` reads a comment's display date via `localDateOf(iso)` (reads the `Date` object's local getters), not `iso.slice(0, 10)`. Slicing a full timestamp's ISO string reads its *UTC* calendar date — for the team's SGT (UTC+8) timezone, anything logged before ~8am local still shows as the previous day. `formatDateShort()` itself is fine as-is for genuine date-only fields (`post.date`, no time component) since it deliberately treats those as UTC midnight; the bug only applies when a full timestamp is truncated to a date string for display.

## Modal close asks before discarding unsaved edits

Both the Post and Idea edit modals snapshot their form state (`postFormSnapshot()`/`ideaFormSnapshot()`, a JSON string of the editable fields) the moment they open, and compare against a fresh snapshot before actually closing. `requestCloseModal()`/`requestCloseIdeaModal()` — wired to the X button, Cancel button, and Escape — `confirm()` before discarding if the two snapshots differ; a clean (unedited) modal closes immediately with no prompt. The plain `closeModal()`/`closeIdeaModal()` functions still exist and are called directly (no confirm) from the actual save/delete/send-to-calendar paths, where closing is the intended outcome of a completed action, not a discard. If you add a new way to close either modal, route it through the `requestClose*` wrapper unless it's genuinely post-save.

**The feedback draft box was invisible to this whole mechanism until it was ported over from the
sibling Flowboard app**, where the identical gap had just been found and fixed. Feedback
(`f-feedback-input` / `i-feedback-input`) writes straight to Firestore the instant Add is clicked
— its own `arrayUnion` call, entirely separate from the form's own save — so a draft still sitting
in the box read as "no changes" to both snapshot functions and vanished silently on close, with no
warning at all. Both snapshots now include `feedbackDraft: fFeedbackInput.value` /
`iFeedbackInput.value`. `openIdeaModal()` already cleared `iFeedbackInput` on open; `openModal()`
never did for the Post side — without that, a draft left over from editing a *different* post
would have silently become part of the *next* post's own baseline, masking it entirely rather than
correctly flagging it as unsaved, so that got added too.

**Save had no equivalent check of any kind, on either form** — closing via Cancel/X/Escape was
protected, submitting the form itself wasn't. Both `postForm`/`ideaForm` submit handlers now check
their feedback input first and `confirm()` before proceeding if it has unsent text ("Save the
post/idea and lose it?"). Deliberately a separate check from the close-side snapshot comparison,
not a reuse of it — the correct framing on Save isn't "discard everything or keep editing," it's
"discard the draft specifically, or go click Add first," which needs its own copy naming the
draft.

## Calendar cadence badge (trailing 4 weeks, not "this page")

`renderCadenceBadge()` counts non-draft posts (`status !== "draft"`) whose `date` falls in the trailing 28 days from today, independent of whatever month/week the calendar happens to be scrolled to — it answers "are we actually keeping pace lately", not a stat about the currently-displayed page. Called from the top of `render()` so it stays in sync with the Month/Week toggle and any filter/data change without needing its own listener. Drafts are excluded on purpose: nothing's actually committed to going out yet, so counting them would overstate real cadence.

The badge itself is a `<button>` (`#cadenceBadge`), not a `<span>` — it shows one number ("~1.3 posts/week"), with the raw count and status caveat in a tap-to-open popover (`#cadenceBadgeDetail`, `.cadence-badge-wrap`/`.cadence-badge-detail` CSS) rather than crammed into the visible text. `title` is still set for a desktop hover shortcut, but the popover is what actually makes that detail reachable on touch devices — `title` alone never shows on tap. Same open/close-on-outside-click shape as the status picker (`closeStatusPicker`).

## Feedback replies (submitFeedbackReply / removeFeedbackReply)

Feedback items on both Post and Idea can now be replied to, not just added/removed. A reply lives as `{text, author, date}` inside `feedback[i].replies` — an embedded array on the feedback item itself, same shape/rationale as feedback being embedded on the post/idea (one `updateDoc` with the whole `feedback` array rewritten, no subcollection, no second listener). `submitFeedbackReply(colRef, docId, list, idx, text)` / `removeFeedbackReply(colRef, docId, list, idx, replyIdx)` are the two shared helpers — `renderFeedbackLog()` renders the nested reply list and a per-item reply row identically for both Post and Idea, and each call site (`submitPostFeedbackReply`/`submitIdeaFeedbackReply` and their matching click handlers) just supplies its own `postsCol`/`ideasCol` + `editingId`/`editingIdeaId`. Removing a reply follows the same "splice-and-rewrite the array" pattern used for removing a top-level feedback item or an idea's own feedback (not Firestore's `arrayRemove()`, which is fragile against plain-object elements) — see "Schema changes" above. `.fb-reply-remove` is hidden in mobile view-only mode (same `.modal.view-only` rule as `.fb-remove`); the reply-add row is not, matching the existing "adding feedback survives the mobile lockdown, removing doesn't" rule.

## Notifications (bell, top-right of the topbar)

Fires on two events: a new feedback item on a post/idea (notifies every name in that post/idea's `owners`) and a reply to a feedback item (notifies that item's original author) — both via the shared `notifyRecipients(recipients, type, itemId, itemKind, itemTitle, snippet)` helper, which also dedupes and skips notifying yourself. Stored in a new `notifications` collection: `{recipient, type, itemId, itemKind, itemTitle, author, snippet, at, read}`.

**`@mentions` in feedback text.** Both feedback events above actually go through `notifyWithMentions(text, primaryRecipients, primaryType, itemId, itemKind, itemTitle)`, which layers a mention pass on top of `notifyRecipients`: `parseMentions(text)` matches `@Name` (case-insensitive) against `getKnownNames()` — every name that's ever been typed as a post/idea Owner, since this app has no fixed team roster — and anyone matched gets a single `type: "mention"` notification instead of the primary type, even if they're also an Owner or the original author (no one gets double-notified for the same event). `wireMentionAutocomplete(inputEl, menuEl)` drives the `@`-triggered dropdown on both feedback textareas (`.mention-menu`/`.mention-option`, `f-feedback-input`+`postFeedbackMentionMenu` and `i-feedback-input`+`ideaFeedbackMentionMenu`) — same interaction as Flowboard's task-comment mention menu, reusing `avatarHtml` for the option rows. There's no per-task assignee to notify here (see "Tasks UI is removed for now" in `content-hub-firebase.html` — `createTaskListInput` is dead code, never wired to any DOM elements), so tagging in feedback text is currently the only way to page a specific person in this app.

`enrichFeedbackText(text)` (used by `renderFeedbackLog` in place of a bare `escapeHtml`) is the display-side half of tagging, plus autolinking: it escapes the text, wraps any `@Name` substring in `.fb-mention` (brand-orange background + text) so a tag reads as a tag, and turns any `http(s)://` URL into a `.fb-link` (brand-orange, underlined, opens in a new tab). It splits the raw text on URLs *first* (`String.split()` with a capturing regex, `FEEDBACK_URL_RE`) and only runs the mention regex over the non-URL segments — doing both passes over the whole string in sequence would risk a mention-shaped substring inside a URL's path/query (rare, but possible) getting a `<span>` spliced into the middle of an `href`. Trailing sentence punctuation (`. , ; : ! ?` and closing brackets/quotes) is stripped off the end of a matched URL before linking it, same trim set `extractDriveFolderUrl()` uses for pasted Drive links, so "check this out: https://x.com." doesn't glue the period into the link. Mention matching uses the same `getKnownNames()` roster as `parseMentions`, tried longest-name-first in one combined regex rather than one `parseMentions`-style `.replace()` pass per name — needed here (and not there) because a naive per-name loop would double-wrap a shorter name that's a prefix of a longer one, e.g. wrapping "@Aqila" again inside an already-wrapped "@Aqila Ramadhani". Flowboard's task-comment log has the identical function (`enrichCommentText`, Tailwind utility classes instead of `.fb-mention`/`.fb-link` CSS rules, sourced from `uniqueValues('assignee')` instead of `getKnownNames()`) — keep both in sync if you touch the matching/linking logic in one.

**A mention must END where the name ends.** Both `parseMentions` (notify side) and
`enrichFeedbackText` (display side) append a shared `MENTION_TAIL = "(?![A-Za-z0-9])"` to their
generated regex. Without it, a known name that happens to be a prefix of a longer word matched
inside it: with "Dee" on the roster (and `getKnownNames()` is built from free-typed Owner fields, so
short names are normal), typing "@Deepak" fired a real `type: "mention"` notification to Dee for a
comment that never named them, and rendered as a half-highlighted `@Dee`+`pak`. Sorting names
longest-first in `enrichFeedbackText` does **not** cover this -- that only handles one known name
being a prefix of another known name, not of an arbitrary word. Keep the constant shared by both
functions rather than inlining the guard twice; they drifted apart once already. Flowboard's
`parseMentions`/`enrichCommentText` carry the identical pair and the identical constant -- all four
were fixed together, and a change to one needs the same change in the other three.

**Deliberately queried without `orderBy`.** The obvious query — `where("recipient", "==", myName), orderBy("at", "desc")` — needs a Firestore composite index (an equality filter plus a sort on a *different* field always does), and a missing index doesn't degrade gracefully: the query just fails outright with nothing but a `console.error`, so notifications would silently never load for anyone until someone noticed and deployed an index. `startListeners()` queries with the equality filter only and sorts `myNotifications` client-side in `renderNotifBell()` instead — avoids the index requirement entirely, at the cost of sorting a list that's realistically never more than a few dozen items long. If you ever add a second `where()`/`orderBy()` to this query, check whether it now needs a composite index before shipping it, not after someone reports notifications are broken.

**No Firestore rule was added for the `notifications` collection.** This app's `firestore.rules` is a single blanket `match /{document=**} { allow read, write: if isMediashock() }` covering every collection — unlike the sister Team Project Manager app, which locks notifications to their addressed recipient with a narrower rule. That means here, technically, any signed-in teammate could read, mark-read, or delete someone else's notification — accepted deliberately, for consistency with how every other collection in this app already works (posts/ideas/feedback are all fully shared with no per-user scoping), and so shipping this didn't require the manual "paste new rules into the Firebase console and publish" step every other write path in this app has always been able to skip.

## Suggestions tab

A shared feedback board for the dashboard itself (not a post or a client project) — separate top-level tab, separate `suggestions` collection: `{text, author, date, replies: []}`. Replies use the exact same embedded-array shape and the same reasoning as feedback replies above. Deliberately **not** logged to the Activity feed (`logActivity` is never called from any of the suggestion/reply/remove handlers) — the tab itself is already the full history, and duplicating every suggestion/reply into Activity would just be noise there. Same reasoning as notifications for why no new Firestore rule was needed: the blanket `match /{document=**}` rule already covers it.

## Idea card drag feedback

The kanban column already highlighted on drag-over (`.kanban-cards.drop-target`), but the card
actually being dragged gave no feedback of its own — no opacity change, no lift, nothing — since
the `dragstart` handler on `.idea-card` only ever called `e.dataTransfer.setData`/set
`effectAllowed`, never added a class. Ported over after the same gap was closed on Flowboard's task
cards: `dragstart` now adds `.dragging` (opacity 0.5, a slight `scale(1.02)` lift, `box-shadow:
var(--shadow)`) and `dragend` removes it. `.idea-card` had no `transition` at all before this — `all:
unset` resets it along with everything else — so one was added specifically for `opacity`/
`transform`/`box-shadow`, matching the properties the new state actually changes. `.kanban-cards`
also picked up a `background-color` transition so the existing drop-target highlight fades in/out
instead of snapping.
